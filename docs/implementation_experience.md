# 第一阶段实施经验

本文总结出行管家从概念设计到本地网页、阿里云服务和微信小程序体验版的第一阶段工程经验。当前版本使用合成数据，重点是建立可信、可验证、可继续扩展的基础框架。

## 1. 先完成可信闭环，再扩展真实能力

第一版最重要的成果不是接入尽可能多的第三方 App，而是建立一个可以运行、验证和继续扩展的工程闭环：

```text
合成行程
  ↓
确定性时间计算
  ↓
Evidence + Verifier
  ↓
网页/小程序展示
  ↓
阿里云健康与能力检查
```

当前版本明确不读取携程、国航、航旅纵横等私有页面，不保存真实行程，也不自动预约车辆。这样既能验证产品交互和决策链路，又不会在数据授权、隐私合规和第三方合作尚未完成时越过边界。

## 2. 大模型与确定性代码必须分工

大模型适合：

- 理解自然语言、短信、通知和截图；
- 抽取行程字段；
- 汇总多源事件；
- 解释建议和展示不确定性。

确定性代码负责：

- 机场流程预算；
- 道路时间分位数；
- 风险缓冲；
- 最晚出发时刻；
- 证据完整性和结果重算。

核心原则是：**模型负责理解和说明，代码负责决定和核验。** 出发时刻不能只由模型自由生成，否则难以回放、测试和追责。

## 3. 交付顺序应保持渐进

实践证明，以下顺序能够显著降低联调成本：

1. 本地 API 与网页；
2. Docker 和本地端到端验证；
3. 阿里云网页/API；
4. 微信小程序；
5. 真实数据、提醒和外部执行能力；
6. 最后再评估原生 App。

小程序应复用已经稳定的 HTTPS API，而不是同时开发一套独立后端。网页先行还可以提前发现路径前缀、反向代理、跨域、错误提示和移动端布局问题。

## 4. 复用云资源，但必须隔离产品

可以复用既有阿里云 ECS、域名和工程经验，但新产品必须使用独立的：

- 仓库和部署目录；
- Compose project；
- 回环端口；
- Nginx 路径；
- systemd 服务；
- 小程序 AppID。

复用客流智能体的小程序 AppID 会覆盖另一个产品的开发版本，因此微信身份必须独立。基础设施可以共享，产品身份和运行单元不能混用。

## 5. 微信小程序发布经验

### 5.1 正式 AppID 不进入公共仓库

公共 `project.config.json` 保持 `touristappid`，正式 AppID 只写入被 Git 忽略的 `project.private.config.json`。项目检查脚本应在发现真实 AppID 被写入受控文件时直接失败。

微信开发者工具在导入项目时可能自动改写 `project.config.json`，增加本地编辑器字段并写入正式 AppID。每次导入、预览或上传后都要检查：

```bash
git diff --check
git status --short
git grep '<正式 AppID>'
```

### 5.2 request 合法域名只配置源站

微信公众平台的 request 合法域名应填写：

```text
https://metro.9m-zx.com
```

不能包含 `/mobility` 路径。应用代码仍可请求
`https://metro.9m-zx.com/mobility/...`。浏览器能访问接口并不代表微信严格域名校验已经通过。

域名保存后，应清理开发者工具网络缓存、重新打开项目，并保持 `urlCheck: true`。最终必须在小程序设置页发起真实的 health/capabilities 检查，而不是关闭校验绕过问题。

### 5.3 上传与体验版是两个步骤

推荐使用微信官方 CLI 生成预览并上传：

```bash
WECHAT_CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli
PROJECT=/absolute/path/to/clients/wechat-miniprogram

"$WECHAT_CLI" islogin
"$WECHAT_CLI" cache --clean network --project "$PROJECT" --lang zh
"$WECHAT_CLI" preview \
  --project "$PROJECT" \
  --qr-format image \
  --qr-output /safe/artifact/path/preview.png \
  --lang zh
"$WECHAT_CLI" upload \
  --project "$PROJECT" \
  --version 0.2.0 \
  --desc "合成行程、可核验建议、证据与运行诊断" \
  --lang zh
```

CLI 显示上传成功后，仍需在微信公众平台的版本管理页面把对应开发版本设为体验版。服务器域名保存、管理员确认、平台协议和体验版选择属于平台管理动作，必要时应由管理员亲自完成。

## 6. 运行时核验比“上传成功”更重要

完成部署至少要验证：

- 微信开发者工具识别的是独立正式 AppID；
- `urlCheck` 保持开启；
- request 域名显示正确；
- health 与 capabilities 均成功；
- 服务版本与上传版本一致；
- 环境、数据范围和 Provider 符合预期；
- 小程序“问题”面板没有项目代码错误；
- iOS 和 Android 体验成员至少各完成一次冷启动。

本阶段联调证明：正式域名请求可在严格校验下成功，服务返回 `0.2.0`、`staging` 和 `synthetic`，说明小程序、微信域名配置、Nginx 与阿里云服务已经形成完整链路。

## 7. GitHub 与部署记录的边界

应该提交：

- 产品、架构和运行文档；
- 小程序框架代码；
- 自动化检查和测试；
- 不含身份信息的发布操作说明。

不应该提交：

- 正式 AppID 的私有覆盖文件；
- AppSecret、后台令牌或登录票据；
- 微信后台截图；
- 真实行程和个人数据；
- 临时二维码和机器相关的上传记录。

二维码、CLI 输出和部署核验记录可以保存在本地忽略目录。GitHub 分支使用 `codex/` 前缀，通过 Pull Request 合并，避免直接修改 `main`。

## 8. 第一阶段最值得复用的结论

1. 先用合成数据验证完整链路，再逐项开放真实数据。
2. 大模型不能替代可重算的时间决策引擎。
3. 共享云资源时，产品身份、端口和部署单元必须隔离。
4. 微信“代码上传成功”不等于“体验版可用”，还要配置域名并完成运行时检查。
5. 正式 AppID 虽不是 AppSecret，也不应写入公共框架仓库。
6. 开发者工具会修改项目文件，发布后必须检查工作区和秘密扫描。
7. 所有后续真实能力都要经过数据授权、隐私、幂等、失败回退和用户确认门禁。

## 9. 下一阶段建议

后续按风险由低到高推进：

1. 完成 iPhone/Android 体验版验收；
2. 建立 `wx.login` 服务端身份与对象级授权；
3. 接入用户主动上传的行程截图和可删除 OCR；
4. 接入官方航班、地图、天气与事件数据；
5. 建立订阅提醒、幂等 Outbox 和取消机制；
6. 通过官方深链或合作接口提供叫车入口；
7. 完成隐私保护指引、用户协议、审核与正式发布；
8. 再评估原生 App 对通知读取和跨 App 协同的必要性。
