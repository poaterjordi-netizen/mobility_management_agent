# 产品范围与用户旅程

## 1. 目标用户

首批用户是国内航班旅客，尤其是：

- 对误机损失敏感的商务旅客；
- 不熟悉机场或需要托运行李的旅客；
- 出发地交通波动较大的旅客；
- 希望提前一天安排网约车的人。

首版只优化“从一个已知出发地前往国内机场”的单程接驳。国际航班、多航段、接机、
高铁、酒店和目的地行程不进入 MVP。

## 2. 核心用户故事

### US-01 创建行程

用户可以手工录入或上传截图，得到候选行程：

- 航班号；
- 出发日期；
- 计划起飞时间；
- 出发机场和航站楼；
- 是否托运行李；
- 出发地；
- 风险偏好。

系统先展示候选值和来源，用户确认后才成为权威 `Trip`。

### US-02 获得出发建议

系统根据航班、机场流程、交通、天气、事件和用户偏好给出：

- 建议叫车时间；
- 建议离开出发地时间；
- 建议到达航站楼时间；
- 最晚安全时间；
- 预计值机/安检/步行时间；
- 风险等级和置信度；
- 数据来源、更新时间和缺口。

### US-03 理解原因

用户可以看到：

- 哪些事实直接影响了结果；
- 相比常规情况增加或减少了多少缓冲；
- 数据冲突时采用了哪个来源；
- 哪些内容是事实、计算、假设或一般解释；
- 如果更改“托运行李/风险偏好/出发地”，结果如何变化。

### US-04 提前一天收到提醒

在 T-24h 左右，系统生成提醒：

> 明天 CAxxxx 计划 xx:xx 起飞，当前建议 xx:xx 出发。天气/道路/机场流程带来 xx 分钟
> 额外缓冲。是否打开网约车预约？

Web 本地阶段只预览提醒；云端阶段先做站内/邮件测试；小程序阶段使用用户主动授权的订阅
消息。任何发送都要幂等并允许关闭。

### US-05 处理变化

航站楼、起飞时间、天气、交通或登机口变化时：

- 重算决定；
- 比较新旧建议；
- 只在变化超过阈值或风险等级改变时提醒；
- 说明变化来源；
- 不因单一低可信社交信号制造恐慌。

### US-06 跳转预约

用户点击后打开官方地图/网约车入口，并带入尽可能少的参数。首版不代表用户确认车型、
价格、优惠、支付或下单。

## 3. 各产品表面的能力差异

| 能力 | 本地 Web | 阿里云 Web | 微信小程序 | 原生 App（候选） |
| --- | --- | --- | --- | --- |
| 手工录入 | 是 | 是 | 是 | 是 |
| 截图/文件导入 | 是 | 是 | 是 | 是 |
| 服务器定时刷新 | 仅开发进程 | 是 | 由后端完成 | 是 |
| T-24 提醒 | ICS/预览 | ICS/预览 | 预览/复制 | 系统日历候选 |
| 订阅/推送提醒 | 否 | 否 | 平台模板与用户授权后 | 系统推送候选 |
| 日历导入 | `.ics` 内容 | `.ics` 内容 | `.ics` 内容 | 系统日历授权 |
| 读取其他 App 通知 | 否 | 否 | 否 | Android 有条件 |
| iOS 跨 App 分享 | 否 | 否 | 否 | Share Extension |
| 后台位置 | 否 | 否 | 受限且不作为首版 | 有条件 |
| 自动下单 | 否 | 否 | 否 | 仍需用户确认/合作 API |

网页和小程序不能实现“读取携程/航旅纵横 App 内部数据”。因此在前三阶段，产品文案必须
说“导入/同步/查询获授权来源”，不能声称“访问手机上的所有 App”。

## 4. 页面信息架构

本地 Web MVP：

1. `Today`：下一次行程、建议时间、风险和数据新鲜度；
2. `Trips`：创建、导入、确认、编辑、删除；
3. `Trip Detail`：时间线、证据、建议、变化历史；
4. `Ask`：受控问答与执行轨迹；
5. `Sources`：已启用来源、权限、上次成功、配额/故障；
6. `Settings`：默认出发地、风险偏好、行李、步行速度、提醒；
7. `Privacy`：授权、导出、删除和数据保留。

小程序在不损失核心流程的前提下合并页面，避免复制 Web 管理后台的所有诊断细节。

## 5. 用户可调参数

- 默认出发地（显示别名，不在普通日志显示完整地址）；
- 到机场偏好：标准/稳妥/非常稳妥；
- 托运行李；
- 国内/国际行程类型；
- 行动不便/步行速度；
- 熟悉机场；
- 网约车预计等待偏好；
- 提醒窗口和免打扰时间；
- 是否允许保存历史用于个性化。

所有个性化只改变确定性参数，不允许模型凭“了解用户”暗中提前或推迟时间。

## 6. 体验原则

- 先给结论，再给原因；
- 同时展示“建议时间”和“最晚安全时间”，但明确后者风险更高；
- 用分钟解释缓冲，不用模糊的“尽早”；
- 风险信息按影响排序，避免社交噪声堆砌；
- 过期、冲突或缺失证据必须可见；
- 用户修改任一输入后立即显示差异；
- 不用“保证赶上”“绝不会误机”等承诺性语言；
- 高风险变化使用明确、可行动的提醒。
